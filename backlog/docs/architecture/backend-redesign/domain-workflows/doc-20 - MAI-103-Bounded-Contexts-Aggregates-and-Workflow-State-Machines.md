- **Language:** English

- **Implementation boundary:** No schema, repository, service, handler, worker, or production code is implemented by this document

## 1. Architectural shape

MAI targets a modular monolith. Each bounded context is a module with owned application services, domain model, persistence schema, repositories, events, and read models. Cross-context work uses stable IDs, application-service calls, and committed domain events; one context never mutates another context’s tables.

There is no universal `Deal` aggregate. `dealId` is a cross-context reference and isolation key. Each context owns the transactional state it can keep consistent in one commit.

The shared kernel is deliberately small:

- `TenantId`, `WorkspaceId`, `DealId`, typed aggregate IDs;
- `AggregateVersion`, `IdempotencyKey`, `CorrelationId`, `CausationId`;
- `Money`, `Currency`, `Period`, `Timestamp`, `Checksum`;
- authenticated `ActorContext` and policy result references;
- domain-event and error envelopes.

Identity, permissions, audit, evidence, jobs, and integrations are not utility bags. They have explicit ownership and contracts.

## 4. Standard transition contract

Every transition row below inherits these mandatory fields unless the row states a stricter rule:

- **Expected version:** current aggregate version via `If-Match`; create commands use absence plus uniqueness.
- **Idempotency:** required for every mutation. Same key, actor, target, command, and payload returns the original result; a changed payload returns `IDEMPOTENCY_CONFLICT`.
- **Authorization:** authenticate and evaluate tenant/workspace/deal/object/field/action/purpose/sponsor/expiry before loading the aggregate. Unauthorized and absent protected targets both return protected `404`.
- **Audit:** append actor, authority snapshot, command, before/after versions, evidence/provenance references, correlation/causation, outcome, and consequence in the same transaction.
- **Failure:** validation `422`; version/stale conflict `409`; invalid transition `409`; dependency or provider unavailable `503`; legal hold `423`; protected not found `404`.
- **AI:** AI/system actors are allowed only where explicitly named. They never satisfy an H-only transition.

## 6. Authority invariants

1. AI cannot approve or reject.
2. AI cannot establish transaction price.
3. AI cannot send a proposal or communicate externally.
4. AI cannot waive a closing condition.
5. AI cannot sign.
6. AI cannot invite or offboard.
7. AI cannot grant or revoke permission.
8. AI cannot release a deliverable.
9. AI cannot archive, restore, terminate, or delete a deal.
10. AI output remains a proposal, recommendation, calculation, plan, or reversible artifact until an authorized human command succeeds.

These invariants are enforced by actor-type checks inside application services, not by prompt text or frontend visibility.
