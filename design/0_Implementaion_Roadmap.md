# 1. Roadmap definition

The **Implementation Roadmap** converts the product architecture into an executable sequence of:

* Product releases;
* domain-model implementation;
* interface development;
* AI and deterministic-engine work;
* security controls;
* validation;
* design-partner POCs;
* enterprise hardening.

It is not a chronological list of screens.

The implementation should build the smallest complete version of M&Ai’s defining transaction loop:

> **Document → Evidence → Structured fact → Finding → Deterministic impact → Human decision → Audit record**

This vertical slice proves the three connected product capabilities:

* Diligence intelligence;
* deterministic valuation;
* workflow orchestration.

The intended product is an auditable deal workspace, not a technical collection of agents or engines. 

---

# 2. Roadmap objective

The roadmap should take M&Ai through four product states:

## State 1 — Credible product prototype

A coherent interface demonstrating the complete evidence-to-decision workflow with fictional data.

## State 2 — Functional MVP

A persisted, deal-isolated application capable of processing controlled historical transaction information.

## State 3 — Design-partner POC

A production-like system supporting narrowly scoped workflows in real transactions under human supervision.

## State 4 — Enterprise-ready platform

A system with verified isolation, security controls, integrations, reliability, retention and auditable administration.

---

The current deck establishes the intended sequence:

* **Q4 2026:** MVP with core workflow, UX validation, evidence-linked extraction and valuation engine;
* **Q3 2027:** three live design-partner POCs, real transaction workflows, evaluation benchmark and customer feedback;

# 4. Roadmap thesis

M&Ai should not be developed screen by screen.

The implementation sequence should be:

```text
Domain foundation
  ↓
Evidence spine
  ↓
Decision-grade vertical slice
  ↓
Banker operating workspace
  ↓
Controlled historical-deal tests
  ↓
Live design-partner POCs
  ↓
Enterprise controls and scaling
```

The Diligence Decision Room remains the defining vertical slice because it simultaneously demonstrates:

* Source-linked findings;
* deterministic financial impact;
* human approval.

That combination is more differentiated than a generic pipeline board or chat interface.

# 6. Release philosophy

Each release must provide a **usable vertical outcome**.

Avoid releases such as:

> “Twelve screens implemented.”

Prefer:

> “A banker can open a changed spreadsheet, inspect the affected fact, review the resulting finding, calculate the valuation impact and record an approved decision.”

A screen is not complete merely because:

* It renders;
* it uses mock data;
* the API returns a successful response;
* the happy path works.

It is complete when:

* Its authoritative object exists;
* state is persisted;
* permissions are enforced;
* errors are honest;
* versions are preserved;
* material actions create audit events;
* dependent screens update correctly.

# 15. R0 architecture decisions

The following decisions should be recorded before R1.

## ADR 1 — Modular monolith first

Use one deployable application with explicit domain modules.

Do not start with numerous microservices.

Reasons:

* Small team;
* evolving domain boundaries;
* easier transactional integrity;
* simpler local development;
* lower operational overhead.

Modules should still communicate through clear interfaces and domain events.

## ADR 2 — PostgreSQL as primary transactional store

Use it for:

* Deals;
* organizations;
* document metadata;
* facts;
* findings;
* scenarios;
* tasks;
* decisions;
* permissions;
* audit references.

## ADR 3 — Object storage for binary artifacts

Use controlled object storage for:

* Documents;
* document versions;
* generated reports;
* submission files;
* audit packages.

## ADR 4 — Transactional outbox

Persist state and material domain events atomically.

## ADR 5 — Server-side authorization

The browser must never be the security boundary.

## ADR 6 — Versioned material objects

Approved and decision-relevant objects require immutable versions.

## ADR 7 — AI creates proposals, not decisions

Human approval remains authoritative.

## ADR 8 — Deterministic engines own financial arithmetic

Language models may help interpret or prepare inputs.

They must not become the final arithmetic layer.

# 28. R1 acceptance targets

Recommended initial gates:

* **100%** of approved facts have at least one resolvable evidence reference.
* **100%** of document versions have checksum and source metadata.
* **100%** of fact approvals preserve exact document versions.
* No cross-deal search or retrieval in authorization tests.
* All extraction failures appear honestly rather than disappearing.
* Required financial fields on the controlled golden dataset meet an agreed precision threshold before POC use.

The exact extraction percentage should be established per field and file type rather than through one aggregate marketing number.

# 30. R1 exit gate

R1 is complete when:

1. A deal can be created from the interface.
2. An Organization can be associated with the deal.
3. Documents persist across restarts.
4. Document versions remain immutable.
5. A spreadsheet cell range can be opened from a fact.
6. A fact can be proposed, corrected and approved.
7. A later document version does not rewrite the approved fact.
8. The changed source creates a new fact-review requirement.
9. Failed processing is retryable.
10. Every material action creates an audit event or durable event ready for R2 audit presentation.

## Stage C — DCF foundation

* forecast;

# 37. R2 deterministic-engine rules

The valuation engine must:

* Accept typed inputs;
* reject missing units;
* reject ambiguous currencies;
* preserve raw decimal values;
* define rounding policy;
* produce a calculation trace;
* record engine and formula versions;
* allow replay using the same input snapshot;
* distinguish execution completion from approval.

# 44. R2 decision gate

A decision may be recorded only when:

* Target version remains current;
* authority remains active;
* evidence package remains valid;
* required deterministic execution completed;
* separation of duties is satisfied;
* approval request remains open;
* no blocking dependency changed.

# 45. R2 acceptance targets

Required:

* Every material finding has resolvable evidence.
* Every deterministic scenario is reproducible within the defined rounding policy.
* Every approval references an exact object version.
* Every decision records authority and evidence snapshots.
* A changed source can mark an affected approval for review.
* Notification read state cannot complete a task.
* An unauthorized user cannot invoke an approval endpoint directly.
* Copilot citations never cross deals in the evaluation suite.

# 46. R2 usability gate

Conduct at least five moderated workflow tests, consistent with the validation approach already recommended for the product. 

Participants should complete:

1. Identify the most material finding.
2. inspect exact evidence.
3. understand the calculation.
4. compare base and risk-adjusted scenarios.
5. approve, reject or request changes.
6. locate the resulting audit record.

The release should not proceed if users consistently:

* Cannot locate evidence;
* confuse engine output with approval;
* misunderstand enterprise versus equity value;
* lose deal context;
* distrust the calculation trace.

**Failure mode:** Findings cite filenames but not exact evidence.

**Control:** Evidence references implemented in R1.

## Risk 3 — Financial error

**Failure mode:** Plausible narrative masks incorrect arithmetic.

**Control:** Deterministic engine, independent reconciliation and versioned inputs.

## Risk 4 — Cross-deal leakage

**Failure mode:** Search, cache or Copilot returns another transaction’s data.

**Control:** Server-scoped authorization, isolation tests and permission-safe indexes.

## Risk 5 — Workflow friction

**Failure mode:** Structured controls take longer than spreadsheets.

**Control:** Moderated user testing and one-click exact evidence navigation.

## Risk 6 — VDR dependency

**Failure mode:** Connector delays block product validation.

**Control:** Controlled uploads and adapter abstraction.

## Risk 7 — Model-provider change

**Failure mode:** Quality changes without detection.

**Control:** Model registry and regression evaluation.

## Risk 8 — Live-deal operational pressure

**Failure mode:** Product failure creates transaction risk.

**Control:** Narrow POC scope, shadow mode and explicit fallback.

## Risk 9 — Security claims exceed implementation

**Failure mode:** Marketing promises unsupported controls.

**Control:** Feature-state labels, assessments and approved claim register.

## Risk 10 — Founder bottleneck

**Failure mode:** Every workflow requires manual intervention.

**Control:** Record interventions and treat repeated support as product work.

# 121. Go/no-go gates

## Do not begin historical deal testing when:

* Data does not persist;
* citations cannot be resolved;
* calculation replay fails;
* authorization is UI-only;
* material history disappears after restart.

## Do not begin live POC when:

* Isolation tests fail;
* security runbooks do not exist;
* backup restore has not been tested;
* model evaluations are unavailable;
* human approval can be bypassed;
* design partner scope is undefined.

## Do not claim enterprise readiness when:

* SSO is absent where required;
* retention is manual;
* critical security findings remain;
* external access lacks expiry;
* audit coverage is partial without disclosure;
* production operations depend solely on founders’ memory.

# 122. Kill or redesign criteria

A workflow should be stopped or redesigned when:

* Bankers cannot verify its sources reliably;
* corrections exceed acceptable operational value;
* the engine cannot reproduce approved numbers;
* the workflow requires more effort than the baseline;
* users interpret AI output as an autonomous decision;
* permission controls cannot be explained;
* support effort scales linearly with each document or user;
* the workflow cannot be scoped safely for a POC.

Do not preserve a feature merely because it was expensive to build.

# 135. Final implementation target

The correct implementation target is not:

> “Build all specified screens.”

It is:

> **Build a deal-isolated execution system where a banker can trace a material transaction conclusion from its exact source through structured analysis and deterministic financial impact to an authorized human decision and immutable audit history.**

The defining implementation sequence is:

> **Establish scope and persistence → build the evidence spine → complete one decision-grade vertical slice → expand into the banker workspace → validate on historical deals → harden for controlled live POCs → add enterprise governance only after workflow value is demonstrated**
