# Agentic Workspace

## 1. Recommended product naming

Use:

* **Deal utility label:** `Agentic Workspace`
* **Page title:** `M&Ai Workspace`
* **Persistent drawer entry:** `Ask M&Ai`
* **Structured unit of work:** `Mission`
* **Conversation container:** `Thread`
* **Execution record:** `Run`
* **Generated output:** `Artifact`

The full workspace should remain a lower-frequency deal utility rather than a principal global destination.

The recommended product model is:

> **Contextual Copilot for immediate questions; full Agentic Workspace for extended investigations and multi-step execution.**

This preserves the deal-centric product architecture. Agents support Diligence, Valuation, Negotiation and Closing rather than replacing those workflows as the navigation system. 

---

# 2. Screen definition

The **Agentic Workspace** is the complete deal-scoped environment where users can instruct M&Ai to investigate, reconcile, calculate, prepare and coordinate multi-step transaction work.

It combines:

* Deal-context conversation;
* Structured missions;
* Specialized-agent delegation;
* Source-linked responses;
* Document retrieval;
* Deterministic-engine execution;
* Tool activity;
* Generated artifacts;
* Human corrections;
* Approval requests;
* Conversation and execution history;
* Failure and recovery states.

It should answer:

1. **What is M&Ai being asked to accomplish?**
2. **Which deal context and sources are in scope?**
3. **Which steps will be performed?**
4. **Which specialized capabilities are involved?**
5. **What evidence was examined?**
6. **Which tools and deterministic calculations were used?**
7. **What output was produced?**
8. **What remains uncertain or incomplete?**
9. **Which material action requires human approval?**
10. **Where should the result be reviewed in the main transaction workflow?**

Its central operating sequence is:

> **User objective → Scoped plan → Agent delegation → Evidence and tools → Structured output → Human review → Audited state change**

The full workspace is intended for long investigations, multi-step workflows, complete conversation history, tool and engine inspection and generated artifacts. It should complement—not replace—the contextual Copilot available throughout the deal. 

---

# 3. Primary intention

## Operational intention

Allow bankers to delegate complex, document-intensive work without losing control over:

* Scope;
* sources;
* assumptions;
* tool execution;
* generated outputs;
* permissions;
* approvals;
* downstream consequences.

## User intention

A banker should be able to say:

> “I can see what M&Ai is doing, what evidence it used, which steps are complete, which assumptions remain uncertain and what requires my decision.”

## Product intention

The screen should make M&Ai’s multi-agent architecture operationally credible.

The product proposition combines:

* Specialized agents;
* deterministic engines;
* tenant- or deal-isolated AI;
* source attribution;
* human approval gates. 

The workspace should expose those capabilities through business workflow—not through infrastructure terminology.

---

# 4. Strategic product role

The Agentic Workspace is important, but it should not be treated as the product’s main visual identity.

Chat interfaces are familiar and visually generic.

M&Ai becomes differentiated when agent work results in:

* An evidence-linked dossier fact;
* a reviewable diligence finding;
* a traceable valuation scenario;
* an approved shortlist;
* a structured counterproposal;
* a controlled closing requirement.

The strongest product model remains:

> **Information → Analysis → Impact → Human decision → Audit record**

The Agentic Workspace initiates and coordinates that sequence. Specialized transaction screens remain the authoritative review and decision surfaces.

---

# 5. What the Agentic Workspace is not

The screen should not become:

* The primary application navigation;
* A generic chatbot;
* A model playground;
* A prompt-engineering console;
* A permanent support widget expanded to full screen;
* A collection of agent personas;
* A raw tool-log viewer;
* A terminal;
* A system-prompt editor;
* A replacement for specialized transaction screens;
* A source-free answer generator;
* An autonomous decision-maker;
* An automatic external-communication system;
* A hidden chain-of-thought viewer;
* A place where every response becomes transaction truth automatically.

The central question is not:

> “What did the AI say?”

It is:

> **“What transaction work was performed, using which evidence, with what output and under whose authority?”**

# 6. Contextual Copilot versus full workspace

## 6.1 Contextual Copilot

Available from every deal screen through:

> **Ask M&Ai**

Best suited for:

* Explaining the selected object;
* summarizing current context;
* finding a source;
* comparing two visible versions;
* drafting a small internal note;
* navigating to relevant work;
* answering a focused question.

The drawer inherits:

* Current deal;
* current page;
* selected object;
* current user permissions.

## 6.2 Full Agentic Workspace

Used for:

* Multi-step investigations;
* cross-workstream reconciliation;
* extended conversations;
* several source and tool operations;
* asynchronous or long-running work;
* artifact preparation;
* approval routing;
* reviewing complete execution history.

## Escalation behavior

The Copilot drawer should include:

> **Open full workspace**

The active conversation, selected object and scope should transfer into the full workspace.

## Return behavior

A mission result should route the user back to the appropriate authoritative screen.

Example:

> Customer-concentration mission completed
> **Review finding in Diligence**

The Agentic Workspace must not become a second, competing version of Diligence or Valuation.

# 9. Core conceptual model

The workspace should separate eight concepts.

## 9.1 Thread

A persistent conversation around a topic.

Example:

> Customer concentration review

## 9.2 Mission

A structured objective containing several steps.

Example:

> Reconcile the latest customer-revenue schedule, reassess concentration and prepare the valuation impact for review.

## 9.3 Step

One observable unit of mission execution.

Example:

> Verify the authoritative revenue schedule.

## 9.4 Agent delegation

Assignment of a step to a specialized capability.

Example:

> Financial Diligence Reviewer

## 9.5 Tool or engine invocation

A bounded operation performed against a source or deterministic system.

Example:

> Run risk-adjusted valuation scenario.

## 9.6 Evidence

Documents, facts, findings, calculations and approved records used in the output.

## 9.7 Artifact

A durable output produced by the mission.

Example:

> Diligence committee brief · Draft v1

## 9.8 Approval request

A proposed material action that cannot occur without human authority.

Example:

> Submit valuation scenario v4 for Deal Lead approval.

---

# 10. Conversation is not the work record

A chat message may initiate work, but the conversation transcript should not be the only representation of that work.

Example user message:

> Review the updated customer-revenue schedule and determine whether the valuation should change.

The system should create:

* A mission;
* a scoped plan;
* execution steps;
* source references;
* calculation runs;
* output artifacts;
* approval requests.

The conversation remains the interaction layer.

The mission remains the operational and auditable layer.

# 14. Objective confirmation

For small, unambiguous requests, execution may begin immediately.

For broad or consequential requests, M&Ai should confirm its interpretation.

Example:

> **Objective understood**

> Reconcile the latest customer-revenue schedule, determine whether the approved concentration fact has changed and prepare—but do not approve—a revised valuation treatment.

Scope:

* Project Horizon only;
* Financial workstream;
* current document versions;
* approved scenario v3 as the comparison baseline.

Primary action:

> **Start mission**

Secondary:

* Edit scope;
* save draft.

---

# 15. Agent operating model

The default interaction should use one user-facing orchestrator:

> **M&Ai Orchestrator**

The orchestrator:

* Interprets the objective;
* proposes a plan;
* delegates bounded steps;
* collects outputs;
* resolves dependencies;
* presents the final result;
* requests approval when required.

The user should not normally need to decide which internal agent class receives every message.

---

# 16. Specialized capabilities

Advanced users may directly select a business capability.

Recommended labels:

| User-facing capability     | Internal direction               |
| -------------------------- | -------------------------------- |
| **Automatic routing**      | Broker or deal orchestrator      |
| **Deal Setup & KYB**       | Sourcing/KYB agent               |
| **Diligence Coordination** | Diligence supervisor             |
| **Financial Review**       | Financial-risk agent             |
| **Legal Review**           | Legal diligence agent            |
| **Valuation Analysis**     | Deterministic valuation workflow |
| **Counterparty Research**  | Matching workflow                |
| **Negotiation Analysis**   | Negotiation agent                |
| **Closing Coordination**   | Legal-closing agent              |

Do not expose internal class names such as:

> `BrokerOrchestratorAgent`

in the standard banker interface.

---

# 17. Agent selection behavior

Recommended default:

> **Automatic routing**

Selecting a specialized capability may be useful when:

* The objective is narrow;
* the user is a specialist;
* a previous automatic route was inappropriate;
* the user wants a second review.

## Selection warning

Direct selection should not expand permissions.

Example:

> Legal Review can only access legal-workstream evidence available to you.

## Unavailable capability

> **Closing Coordination unavailable**

Reason:

> No approved commercial baseline exists.

---

# 18. Multi-agent delegation

The workspace should show delegation as a structured plan.

Example:

```text
M&Ai Orchestrator
  ├── Document Review
  │     Verify the current customer-revenue schedule
  ├── Financial Diligence
  │     Recalculate concentration and assess threshold breach
  └── Valuation Analysis
        Calculate the proposed scenario impact
```

The user should be able to understand:

* Which capability owns each step;
* why the capability is involved;
* whether the step is running;
* what it produced;
* whether it failed.

Avoid anthropomorphic agent avatars having a visible group conversation.

---

# 19. Work trace, not private reasoning

The screen should expose an **execution trace**, including:

* Objective;
* plan;
* step status;
* delegation;
* sources opened;
* tools used;
* calculations performed;
* assumptions;
* outputs;
* errors;
* unresolved questions;
* approvals.

It should not expose:

* Hidden chain-of-thought;
* private model scratchpads;
* internal system instructions;
* token-by-token reasoning;
* raw hidden prompts;
* speculative internal deliberation.

Use concise rationale such as:

> The latest schedule was selected because it is the current authoritative version and covers the LTM period.

Do not show unrestricted internal reasoning logs.

# 20. Recommended workspace structure

The full workspace should contain five principal regions:

1. **Mission and thread navigator**
2. **Conversation and result canvas**
3. **Execution plan**
4. **Evidence, tools and artifacts inspector**
5. **Approval and action surface**

Recommended top-level views:

* **Work**
* **Conversations**
* **Runs**
* **Artifacts**
* **History**

The default should be **Work**.

# 29. Cross-deal boundary

The deal-level Agentic Workspace should not search another transaction by default.

A cross-deal request should require:

* Explicit user intent;
* institution-level permission;
* authorized data policy;
* clear source attribution;
* separate context mode.

Example:

> **Cross-deal analysis unavailable in this workspace**

> Open institution research with authorized deal selection.

This protects transaction isolation and prevents accidental information leakage.

# 34. Response structure

A substantial response should use a predictable format.

## Recommended structure

### Result

Direct conclusion.

### Key evidence

Source-linked facts.

### Analysis

Structured interpretation or calculation.

### Limitations

Missing or uncertain information.

### Proposed next action

A reversible recommendation.

### Actions

Buttons routing to exact context.

## Example

> **Result**

> The top-three customer concentration increased from 39,8% to 41,2%. The current finding remains valid and the revised valuation scenario decreases the midpoint by R$ 42 mi.

> **Limitations**

> FY2023 monthly customer detail remains unavailable, so the longer-term trend cannot yet be confirmed.

Actions:

* Review finding;
* inspect valuation;
* draft information request.

# 45. Agent versus engine distinction

The interface should distinguish:

## Agent

Interprets the objective, gathers context and coordinates work.

## Deterministic engine

Performs a reproducible calculation from explicit inputs.

Example:

> Financial Review proposed a 5,0% revenue downside.

> The Valuation Engine calculated the resulting range.

The agent does not “calculate” an opaque valuation in prose.

---

# 46. Side-effect classification

Actions should be classified by consequence.

## Level 1 — Read-only

May execute automatically within permissions.

Examples:

* Search documents;
* retrieve approved facts;
* inspect a scenario;
* compare versions.

## Level 2 — Reversible internal draft

May execute automatically with explicit draft state.

Examples:

* Draft an information request;
* prepare a report;
* create a proposed finding;
* build an unsubmitted scenario.

## Level 3 — Material internal state change

Requires approval or explicit confirmation.

Examples:

* Approve a dossier fact;
* submit a finding;
* mark a scenario current;
* change a shortlist;
* create a closing waiver request.

## Level 4 — External or irreversible action

Requires explicit authorized confirmation.

Examples:

* Send an information request;
* contact a counterparty;
* circulate a term sheet;
* grant VDR access;
* authorize closing;
* send payment instructions.

---

# 47. Approval request

## Required information

* Proposed action;
* reason;
* affected object;
* material impact;
* evidence;
* required authority;
* side effects;
* alternative actions.

## Example

> **Submit valuation scenario v4 for approval**

> Enterprise-value midpoint decreases by R$ 42 mi.

Affected:

* Deal Overview;
* valuation report;
* negotiation reference range.

Required authority:

> Deal Lead

Actions:

* Review scenario;
* request changes;
* dismiss proposal.

The full decision should normally occur in the authoritative workspace.

# 98. Repository direction

The current repository already contains useful foundations:

* Deal-scoped threads;
* message history;
* agent selection;
* streamed responses;
* SSE reconnection;
* cancellation;
* retry;
* citation types;
* tool-started and tool-completed events;
* VDR-document references;
* engine-run references;
* a three-column workspace structure.

These foundations should be retained selectively.

The MAI-52 rebaseline correctly identifies that current execution remains incomplete: the Broker is effectively the only active route, streaming can be artificial, citations may be empty, tool traces may not be emitted and engine or VDR outputs may fall back to fixture-like defaults. The final screen must expose only truthful integrated behavior. 

## Keep

* Thread persistence;
* streamed-response transport;
* reconnect using stable message identity;
* cancel and retry;
* citation event model;
* tool event model;
* responsive three-region architecture;
* message-history loading;
* empty and error states.

## Add

* Mission model;
* explicit plans and steps;
* automatic orchestration;
* real specialist delegation;
* tool and engine provenance;
* context snapshots;
* artifact registry;
* side-effect policy;
* human approval requests;
* corrections and dependency invalidation;
* truthful background-run state;
* exact specialized-workspace handoffs;
* permission-aware agent capability;
* audit and reproducibility records.

## Replace

### Raw agent tabs

Replace internal names such as:

* BrokerOrchestrator;
* FinancialRisk;
* LegalDD;
* Negotiation;

with business capabilities and automatic routing.

### Generic insight cards

Replace permanent cards such as:

* Financial risk score;
* deal match score;
* valuation range;

with mission-relevant results and links to their authoritative screens.

### Default score fallback

A missing engine result must not display a fabricated fallback such as:

> 2,4 / 5,0

Use:

> Analysis not run

or:

> Result unavailable

### Raw JSON

Tool and engine results should use domain components.

Raw JSON may remain in advanced diagnostics.

### VDR document card

Replace the generic ingested-document list with:

* Context used;
* current sources;
* citations;
* exact evidence locations.

## Locale correction

Current monetary and date formatting should move from `en-US` presentation to pt-BR conventions for the product locale.

Examples:

* `R$ 480 mi–R$ 520 mi`
* `41,2%`
* `28 jul. 2026`

# 115. Design validation criteria

The Agentic Workspace is ready for approval when:

1. It remains deal-scoped by default.
2. It is not a primary global-navigation destination.
3. Contextual Copilot and full workspace have distinct roles.
4. Threads and missions are distinct.
5. Multi-step work creates a structured mission record.
6. Automatic routing is the default.
7. Internal agent class names are not required for normal use.
8. Users can inspect and edit the mission plan.
9. The interface shows execution trace without exposing private chain-of-thought.
10. Every material claim can expose its source.
11. Citation versions remain historically resolvable.
12. Agents and deterministic engines are visibly distinct.
13. Tool outputs use business-readable components.
14. Raw JSON is restricted to advanced diagnostics.
15. No fabricated default result appears.
16. Artificial streaming cannot appear as live execution.
17. Completed steps survive connection interruption.
18. Partial completion remains usable.
19. Missing evidence is stated explicitly.
20. User corrections identify affected outputs.
21. Deal memory is inspectable and scoped.
22. Restricted information cannot leak through tool traces.
23. Document instructions cannot override mission policy.
24. External actions require explicit authorization.
25. Material state changes require approval.
26. Approvals route to authoritative transaction screens.
27. Generated artifacts have version and review states.
28. Missions record context, sources, tools and approvals.
29. A completed mission has a reproducibility state.
30. Specialized-screen handoffs preserve exact context.
31. The screen remains useful without direct agent selection.
32. The screen remains useful without every agent capability being live.
33. Mobile supports monitoring, correction and approval.
34. Streaming updates are accessible.
35. The pitch mock remains fictional.
36. The static image does not resemble a generic chat product.
37. The interface does not imply autonomous transaction judgment.
38. Every mission state has a clear next action.

# 116. Final design target

The correct design target is not:

> “A sophisticated chat interface for several AI agents.”

It is:

> **A deal-isolated execution workspace where bankers can delegate complex transaction work, observe the plan and evidence, correct the process and retain final authority over every material output.**

Its defining interaction is:

> **State the objective → confirm the scope → observe the plan → inspect the evidence and calculations → correct where necessary → review the output → authorize the next transaction action**
